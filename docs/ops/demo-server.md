# Public demo server

One documented command sequence turns a fresh small VPS into `https://demo.civora.sk` (the domain is a placeholder, set your own in `.env`): the host app with the engine (pinned in the `Gemfile`, currently v1.7.1), a Caddy TLS terminator with automatic Let's Encrypt certificates, and **demo data only**.

Background: [ADR-011](https://github.com/civora-org/civora-platform) (hosting model), [civora-platform#168](https://github.com/civora-org/civora-platform/issues/168) (TLS terminator and `DECIDIM_FORCE_SSL`). The TLS part is a separate reusable overlay, see [TLS terminator](#tls-terminator-also-for-production).

## Do not put real data on it

The demo is public, unbacked-up and wiped on request or every night.

- No real contracts, no real people, no real e-mail addresses. Seeds and the demo admin use fictional data and `example.org` addresses.
- No real CRZ: `CRZ_ICO_ORG_*` stays unset, the CRZ scheduler does not start, and `bin/demo-deploy` refuses a `.env` that sets it.
- No real mail: with `DEMO_MODE=1` the app writes outgoing mail to files in the container (`tmp/demo-mails`); `SMTP_*` stays unset and is refused by the script.
- No municipality pilot on this server. A pilot gets its own stack and its own database (README, "Pilot readiness checklist").
- Search engines are kept out: `X-Robots-Tag: noindex` on every response and a disallow-all `robots.txt`, both served by Caddy.

Every page carries a banner "DEMO — fiktívne údaje" (Decidim's omnipresent banner, an organization setting written by `civora:demo:prepare_server`).

## What it costs

About 5 to 10 EUR per month: a 2 vCPU / 4 GB VPS in the EU (for example Hetzner CX22, about 4 to 5 EUR; check the current price list) plus nothing else. The domain is the one you already own. Let's Encrypt is free.

## Steps for the human

### 1. Rent the VPS

- 2 vCPU / 4 GB RAM, 40 GB disk, Debian 12 or Ubuntu 24.04, EU location.
- Add your SSH public key at creation (root login with key). Note the public IPv4 address.

### 2. Point DNS

Create an `A` record `demo.civora.sk` (or your name) to the VPS IPv4 address (add `AAAA` for IPv6 if you want it). Wait until `dig +short demo.civora.sk` shows the address. Without it Let's Encrypt cannot issue the certificate and the deploy smoke check fails.

### 3. Create a read-only GitHub token

The host repository and the engine gem are private. Create a **fine-grained personal access token** in GitHub, Settings, Developer settings:

- Resource owner: `civora-org`, repositories: `civora-host` and `decidim-contracts_sk`.
- Permission: Contents, **read-only**. Nothing else.
- Short expiry (for example 90 days).

It is the same kind of token as CI's `ENGINE_READ_TOKEN`. The image build reads it as a BuildKit secret (`secrets: github_token` in `compose.yaml`), never as a build argument, and it is not stored in any image layer. On the server it lives in `~deploy/.config/civora-demo/github-token` (mode 600), **outside** the repository directory, so it is neither in the build context nor in the app container's environment.

### 4. Provision the server (once, as root)

The script is in the private repository, so copy it from your checkout:

```bash
scp bin/demo-provision root@<VPS-IP>:
ssh root@<VPS-IP>
GITHUB_TOKEN=<the token> SITE_ADDRESS=demo.civora.sk ACME_EMAIL=you@example.org \
  INSTALL_RESET_CRON=0 bash demo-provision
```

(Type the token on the server only; do not paste it into chat, tickets or shell history you share.) The script is idempotent. It installs Docker and the compose plugin from Docker's official apt repository, creates the `deploy` user (in the `docker` group, with your SSH keys), enables UFW with only ports 22, 80 and 443, turns on unattended security upgrades, adds a 2 GB swap file because the image build needs the headroom on a 4 GB machine, stores the token, clones the repository to `~deploy/civora-host` and creates `.env` from `.env.demo.example` (mode 600).

### 5. Fill `.env`

```bash
ssh deploy@<VPS-IP>
cd civora-host
nano .env
```

Check `SITE_ADDRESS`, `ACME_EMAIL`, `DEMO_ADMIN_EMAIL`. `SECRET_KEY_BASE` and `POSTGRES_PASSWORD` are generated by the deploy script when empty (do not change `POSTGRES_PASSWORD` after the first deploy: the database volume already holds it). Every variable is explained in [`.env.demo.example`](../../.env.demo.example).

### 6. Deploy

```bash
bin/demo-deploy
```

The first run builds the image (about 10 to 15 minutes on 2 vCPU), starts Postgres, Redis, the app and Caddy, creates and migrates the database (`db:prepare` on app boot), seeds the organization for your host, runs `civora:demo:prepare_server` (Slovak locale, demo banner, demo admin), `decidim_contracts_sk:seed_demo` (fictional contracts in every lifecycle state) and `civora:demo:proposal_to_contract` (the proposal-to-contract story, [demo-proposal-to-contract.md](demo-proposal-to-contract.md)), then smoke-checks `https://<host>/up` and `/contracts` (200), the HTTP to HTTPS redirect and `robots.txt`. It retries for about 3 minutes while the certificate is issued.

Flags: `--pull` (fast-forward the checkout first), `--skip-build`, `--reset` (see below). Re-running without flags is safe: it only rebuilds from cache, applies migrations and re-runs the idempotent seeds.

### 7. Log in

The demo admin e-mail is `DEMO_ADMIN_EMAIL`. The password was generated by the script and written **only** to `~/.civora-demo-admin` on the server (mode 600, readable by the deploy user and root; never printed and never in `.env`):

```bash
cat ~/.civora-demo-admin
```

Sign in at `https://<host>/users/sign_in`, then use `/admin` and `/contracts/admin/contracts`. With the four-eyes rule one admin cannot approve their own submission; the seed also creates `contracts-editor@example.org` and `contracts-admin@example.org` (unknown random passwords). For a two-person walkthrough create a second admin in `/admin` with a fictional address, or reset one of them from `rails console`.

### 8. Optional: nightly reset (drop and reseed)

Keeps the demo from drifting after visitors click around. Install either at provision time with `INSTALL_RESET_CRON=1`, or later as root:

```bash
cat >/etc/cron.d/civora-demo-reset <<'CRON'
30 3 * * * deploy cd /home/deploy/civora-host && bin/demo-deploy --reset --skip-build >>/home/deploy/demo-reset.log 2>&1
CRON
```

`--reset` stops the app, drops and recreates the database, empties uploads and mail files, then reseeds with the same admin password. The site returns 502 for about two minutes while it boots. Remove the file to stop it. Run it by hand the same way before a presentation.

## Memory budget

`compose.demo.yml` limits the containers for a 4 GB machine: app 1.7 GB (3 threads, one process), Postgres 512 MB, Redis 128 MB, Caddy 128 MB, about 2.5 GB in total; the rest is for the OS and the page cache. Image builds run outside those limits and use the swap file.

## Observability is not included

`compose.observability.yml` (GlitchTip, Prometheus, Alertmanager, blackbox, pushgateway) adds roughly 2 GB and its own Postgres. It is **not** part of the demo. If you want it, use a VPS with at least 8 GB and add the file to `COMPOSE_FILE` in `.env`, then follow [observability.md](observability.md). A cheaper substitute: an external uptime check on `https://<host>/up`.

## TLS terminator (also for production)

`compose.tls.yml` is the reusable part and covers [civora-platform#168](https://github.com/civora-org/civora-platform/issues/168) for any single-host stack, production included:

```bash
# .env: SITE_ADDRESS=<host>  ACME_EMAIL=<contact>  (DNS A record in place, 80/443 open)
docker compose -f compose.yaml -f compose.tls.yml up -d      # or COMPOSE_FILE=... in .env
```

- Caddy (`deploy/caddy/Caddyfile`) gets and renews Let's Encrypt certificates, redirects HTTP to HTTPS and forwards `X-Forwarded-Proto/-For/-Host`. Certificates live in the `caddy-data` volume: keep it, or Let's Encrypt rate limits bite on rebuilds.
- `DECIDIM_FORCE_SSL=1`: Rails redirects any plain request, sends HSTS and secure cookies, and Decidim builds https links in mail and feeds.
- The app's port 3000 mapping is removed (`ports: !reset []`). Docker publishes ports around UFW, so the base mapping would expose plain HTTP.
- The in-container healthcheck sends `X-Forwarded-Proto: https`, because with `force_ssl` a plain probe would only see a redirect.
- Per-environment extras go in `deploy/caddy/*.caddy` snippets mounted to `/etc/caddy/site.d/` (the demo overlay mounts `demo.caddy`).
- Production adds its own overlay for backups and observability on top; this overlay does not change them. Before a pilot also see README "Pilot readiness checklist" (SMTP, backups).

`compose.demo.yml` adds `DEMO_MODE=1`, the memory limits, the disabled CRZ scheduler (compose profile `crz-sync`) and the noindex snippet.

## Operating it

```bash
cd ~/civora-host
docker compose ps
docker compose logs -f app caddy
bin/demo-deploy --pull          # update to the latest main
```

Updating the engine means bumping the tag in the `Gemfile` through a host PR, then `bin/demo-deploy --pull`.

## Teardown

On the VPS (deletes all demo data, certificates and images):

```bash
cd ~/civora-host && docker compose down -v --rmi local
sudo rm -f /etc/cron.d/civora-demo-reset
```

To stop paying, **delete the VPS in the provider console** (stopping it still bills), remove the DNS record, and revoke the GitHub token (Settings, Developer settings, Fine-grained tokens).

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Smoke check never gets a 200 over https | DNS A record missing or not yet propagated; ports 80/443 closed at the provider's firewall; `docker compose logs caddy` shows the ACME error |
| `docker: permission denied` as deploy | Log out and in once after provisioning (docker group) |
| Build fails at `bundle install` with a git auth error | The token lacks read access to `decidim-contracts_sk`, or expired |
| App stays unhealthy | `docker compose logs app`; usually a wrong `POSTGRES_PASSWORD` after the volume was created with another one (`docker compose down -v` on a demo is fine) |
| Build killed (exit 137) | Out of memory: check `swapon --show`, or use a 4 GB plan |
